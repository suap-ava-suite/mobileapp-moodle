VALIDAÇÃO EM DISPOSITIVO REAL

Compilar e testar no celular Android

O fluxo normal de validação usa um aparelho físico conectado por USB. O repositório não exige emulador. Separe build, instalação e validação autenticada: são etapas diferentes.

Preserve a sessão: sem autorização explícita, não instale ou substitua APK, desinstale, limpe dados/cache, faça logout, troque a conta, altere permissões nem reinicie o aparelho. Não execute ações que toquem em telas sensíveis em nome do usuário.

01 · PREPARAR O APARELHO

Depuração USB e identificação

  1. No aparelho, abra Configurações → Sobre o telefone e toque sete vezes em Número da versão (o rótulo varia conforme fabricante) para habilitar as opções do desenvolvedor.
  2. Em Opções do desenvolvedor, habilite Depuração USB. Confirme o diálogo de confiança no aparelho quando conectá-lo ao computador.
  3. Conecte por cabo de dados e consulte a saída antes de usar qualquer comando direcionado ao dispositivo.
Diagnóstico somente leituraPowerShell, macOS ou Linux
adb devices -l
adb shell getprop ro.product.model
adb shell getprop ro.build.version.release
adb shell getprop ro.build.version.sdk
adb shell dumpsys package com.moodle.moodlemobile

Confira o estado device, modelo, versão Android/API e metadados do package. Se houver mais de um aparelho, use adb -s <SERIAL> depois de identificar o alvo; não registre o serial em documentação pública.

Se o status mostrar unauthorized, desbloqueie o aparelho e aceite o diálogo de depuração. Não revogue autorizações nem altere outras opções como tentativa automática de diagnóstico.

02 · BUILD

Compilar sem instalar

Confirme as versões e os requisitos Android do repositório no manual principal. O projeto usa com.moodle.moodlemobile; o identificador não prova que uma APK tem a mesma assinatura da versão instalada.

Ordem do build debug no Windows PowerShellRaiz do repositório
npm.cmd run build:mobilemoodle
node src/MoodleIFRN/build-native.mjs --platform=android
.\node_modules\.bin\cordova.cmd prepare android
.\node_modules\.bin\cordova.cmd build android --debug

build:mobilemoodle regenera o painel IFRN. build-native.mjs gera a aplicação web Cordova/idioma. prepare aplica hooks e prepara Android. build --debug compila; estes comandos não instalam a APK.

A APK debug normalmente fica em platforms/android/app/build/outputs/apk/debug/app-debug.apk. Confirme a saída efetiva do Gradle antes de usar esse caminho.

03 · VERIFICAR O ARTEFATO

Package ID, assinatura e hash

Antes de qualquer instalação, compare o package ID e os certificados da APK com o aplicativo já instalado. Uma incompatibilidade de assinatura impede atualização no lugar; desinstalar para contornar isso apaga os dados locais e não é permitido sem autorização.

PowerShellMetadados locais
$apk = 'platforms/android/app/build/outputs/apk/debug/app-debug.apk'
Get-FileHash -LiteralPath $apk -Algorithm SHA256
$bt = Get-ChildItem "$env:ANDROID_HOME/build-tools" -Directory | Sort-Object { [version]($_.Name -replace '-.*$', '') } -Descending | Select-Object -First 1
& "$($bt.FullName)/aapt.exe" dump badging $apk
& "$($bt.FullName)/apksigner.bat" verify --print-certs $apk

Requer Android SDK configurado em ANDROID_HOME e Build-Tools. Guarde hash e certificado no registro de build; não copie chaves privadas ou credenciais.

Comparar com a assinatura instalada (somente leitura)Copie apenas o APK estático
adb shell pm path com.moodle.moodlemobile
$deviceApk = Read-Host 'Cole o caminho base.apk retornado, sem o prefixo package:'
adb pull $deviceApk .\\installed-app.apk
& "$($bt.FullName)/apksigner.bat" verify --print-certs .\\installed-app.apk

Compare os certificados impressos. adb pull copia o pacote instalado; não lê os dados privados da aplicação. Em instalações divididas, use o caminho do APK base.

Instalar é uma operação separada. Só após autorização explícita, seleção do aparelho e confirmação de package/certificado, use $serial = Read-Host 'Serial do aparelho escolhido' e depois adb -s $serial install -r $apk. Não desinstale para contornar assinatura incompatível: isso apaga os dados locais e pode perder a sessão real.

04 · EXECUÇÃO E DIAGNÓSTICO

Abrir e observar o aplicativo

Depois de uma instalação autorizada, o usuário pode abrir o app pelo launcher. Para iniciar a activity pelo ADB, este comando apenas coloca o app em primeiro plano, mas ainda pode reabrir uma sessão existente; use-o somente como parte de uma validação combinada:

adb shell monkey -p com.moodle.moodlemobile 1

Para logs, capture apenas a janela de tempo necessária. Saídas podem conter URLs, identificadores ou material de sessão; revise e sanitize antes de salvar ou compartilhar. Não use adb logcat -c, pois isso apaga o buffer de logs.

Logcat filtrado por PIDApós abrir o app
$appPid = adb shell pidof com.moodle.moodlemobile
adb logcat -v time --pid=$appPid

Interrompa a captura com Ctrl+C. Redija credenciais, tokens, cookies, URLs privadas e dados acadêmicos antes de anexar evidências.

Inspecionar a WebView

Em uma build que permita depuração WebView, conecte o aparelho, abra Chrome no computador e use chrome://inspect/#devices. Só inspecione a WebView autorizada; evite copiar storage, cookies, tokens ou dados do estudante. Builds de produção podem desabilitar a depuração.

05 · ROTEIRO MANUAL

Validar navegação, toque e curso

  1. Registre a branch, commit, hash da APK, package ID, certificado, modelo e Android API.
  2. Com o usuário presente, valide Marketplace → login oficial SUAP → Painel. Anote se a conta já tinha sessão Moodle.
  3. Abra uma disciplina específica, aguarde a tela nativa e verifique o tema IFRN, conteúdo, loading e retorno ao Painel.
  4. Repita apenas os cenários autorizados de primeira abertura, abertura recorrente e troca de conta. Não troque nem faça logout por conta própria.
  5. Para problemas de toque, registre tela/elemento, WebView ou navegador, orientação, versão Android, resultado de VLibras e logs sanitizados. Não conclua que há sobreposição só pelo sintoma.

Unidade e integração automatizadas não substituem este roteiro. O estado de validação atual e as pendências ficam em Progresso do projeto e Problemas conhecidos.
